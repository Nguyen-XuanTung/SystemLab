# Simulation Engine Specification — SystemLab

This document defines the exact mathematical and behavioral semantics of `src/engine/`.

---

## 1. Virtual Clock & Event Scheduler

- **Virtual Time:** Maintained strictly in milliseconds (`nowMs >= 0`) by `VirtualClock` (`src/engine/core/clock.ts`). Wall-clock time (`Date.now()`, `performance.now()`, `setTimeout`) NEVER participates in latency, timeouts, arrivals, or utilization calculations.
- **Priority Queue:** Binary `MinHeap<SimEvent>` (`src/engine/core/minHeap.ts`) ordered deterministically by tuple:
  1. `timestampMs` (ascending)
  2. `priority` (ascending integer from `EVENT_PRIORITY`)
  3. `sequence` (ascending strictly monotonic insertion counter)
- **Event Priority Order at Equal Timestamps:**
  - `10`: Fault lifecycle & infrastructure transitions (`NODE_FAILED`, `NODE_RECOVERED`, `FAULT_ACTIVATED`, `FAULT_EXPIRED`, `CIRCUIT_HALF_OPEN`)
  - `20`: Service & job completions (`SERVICE_COMPLETED`, `JOB_COMPLETED`) — frees worker slots before new arrivals at the same instant
  - `30`: Request routing & arrivals (`REQUEST_ARRIVED`, `REQUEST_FORWARDED`, `RETRY_SCHEDULED`)
  - `40`: Traffic generation (`REQUEST_CREATED`)
  - `50`: Expiration checks (`REQUEST_TIMEOUT`) — allows a completion scheduled at the exact timeout instant to win cleanly
  - `90`: Telemetry snapshots (`METRICS_TICK`)

## 2. Deterministic Seeded PRNG (`src/engine/random/prng.ts`)

- Seed integer initializes `SplitMix32`, which expands into 4x 32-bit state words for `xoshiro128**`.
- `nextFloat()` produces IEEE-754 uniform values in `[0, 1)`.
- **Independent Substreams (`fork(salt)`):** Telemetry reservoir sampling uses a forked RNG stream (`rng.fork('metrics-reservoir')`) so latency sampling never alters traffic generation, routing, or cache decisions.
- **Arrivals:**
  - `constant`: fixed inter-arrival `1000 / ratePerSecond` ms.
  - `poisson`: exact exponential inter-arrival `-Math.log(1 - u) / (ratePerSecond / 1000)` ms (where `u < 1 - 1e-12`).
  - `bursty`: alternating high-rate bursts (`burstDurationMs`, `burstMultiplier`) and baseline intervals.
  - `ramp`: piecewise-linear rate increase from `0.25 * rate` to `rate` across `durationMs` (updated smoothly at each arrival).
  - `step`: alternates baseline rate and `burstMultiplier * rate` in equal discrete steps.
- **Service Time Distributions:**
  - `fixed`: exact `meanMs`.
  - `exponential`: `-meanMs * Math.log(1 - u)` clamped to `>= 0.01` ms.
  - `lognormal`: exact Box-Muller normal transformed with specified coefficient of variation `cv = sigma / mean` (`mu = ln(mean) - 0.5 * sigmaLn^2`, `sigmaLn = sqrt(ln(1 + cv^2))`).

## 3. Request Lifecycle & Conservation Invariant

Every logical request generated by a `client` receives a unique `req-<n>` identifier and enters `inFlight`.

- A logical request can transition to **at most one terminal state**:
  - `succeeded`
  - `failed`
  - `timed_out`
- **Conservation Invariant:** At every point in simulation time:
  $$\text{generated} = \text{succeeded} + \text{failed} + \text{timedOut} + \text{inFlight}$$
- **Retries:** Local retries on `app_server` reuse the original `requestId` and do NOT increment `generated` or double-count terminal outcomes.
- **Node Failure & Epoch Protection:** Each processing node holds a `nodeEpoch` counter. When a `node_failure` fault triggers:
  - Currently active in-service requests on that node fail immediately (unless already terminal), `activeCount` resets to `0`, and `nodeEpoch` increments.
  - Queued requests on that node fail immediately with `NODE_FAILED` and clear the queue.
  - Any stale `SERVICE_COMPLETED` event carrying an older `nodeEpoch` becomes an explicit no-op, preventing negative `activeCount` or double terminal outcomes.
- **Late Completion After Timeout:** If `REQUEST_TIMEOUT` fires while a request is still in service on a node, the logical request transitions to `timed_out` once; when `SERVICE_COMPLETED` later fires at the server, the worker slot is still released and the next queued request starts, without emitting a second request outcome.

## 4. Component Models & Explicit Simplifications

1. **`client` (Traffic Generator):** Generates read/write requests according to workload mode and schedules `REQUEST_TIMEOUT` at `createdAtMs + timeoutMs`.
2. **`load_balancer`:** Supports `round_robin`, `random`, and `least_in_flight` (`activeCount + queueLength`, breaking ties deterministically by edge order). Health-aware mode skips downstream nodes currently marked `failed`.
3. **`api_gateway`:** Applies continuous-time **Token Bucket** rate limiting (`capacity = burstSize`, `refillRate = rateLimitRps`). Supports `default` or `read_write_split` edge routing.
4. **`app_server`:** Multi-server worker pool (`concurrency`) + bounded FIFO queue (`queueCapacity`), configurable service latency distribution, base failure probability, and bounded local retries (`maxRetries`, `retryDelayMs`).
5. **`cache` (Explicit Probabilistic Model):** Models read hits via `hitProbability` (plus optional linear `cold_start` warmup curve when a cache cold-start fault triggers). On `CACHE_HIT`, serves after `lookupLatencyMs`. On `CACHE_MISS` or `write` (`write_through` / `bypass`), forwards downstream. **Simplification:** Does NOT track individual keys or LRU/LFU eviction sets.
6. **`database`:** Connection-pool limited (`maxConnections`) + bounded FIFO queue with distinct `readLatencyMs` and `writeLatencyMs`.
7. **`message_queue` & `worker`:** In `async_ack` mode, enqueuing succeeds the client HTTP request immediately after `enqueueLatencyMs` and inserts an asynchronous background job pulled by healthy downstream `worker` nodes. In `sync_wait` mode, the client request remains in flight until a `worker` completes the job. Queue tracks separate `jobsEnqueued`, `jobsCompleted`, `jobsFailed`, and `queueDepth`.
8. **`circuit_breaker`:** Stateful `CLOSED` / `OPEN` / `HALF_OPEN` machine tracking consecutive downstream failures (or sliding failure count), tripping to `OPEN` for `openDurationMs`, allowing `halfOpenMaxProbes` probes in `HALF_OPEN`, and resetting to `CLOSED` on probe success.
9. **`read_replica`:** Serves `read` requests using `readLatencyMs` and `maxConnections`; explicitly fails `write` requests (`WRITE_TO_READ_REPLICA`).

## 5. Metrics & Percentile Definitions

- **Throughput (RPS):** $\frac{\text{succeeded}}{\max(\text{horizonMs}, 1) / 1000}$. (In charts, bucket throughput equals bucket completions divided by bucket seconds.)
- **Error Rate (%):** $\frac{\text{failed} + \text{timedOut}}{\max(\text{succeeded} + \text{failed} + \text{timedOut}, 1)} \times 100$ (or `null` / `—` when zero completed/terminal requests exist).
- **Latency Percentiles (`P50`, `P95`, `P99`):** Computed over `succeeded` logical requests using **R-7 linear interpolation** ($h = p \cdot (n - 1)$ on sorted reservoir samples). Returns `null` (rendered as `—`) when sample count is `0`.
- **Node Utilization (%):** Time-weighted integral updated on every concurrency/capacity transition:
  $$\text{utilization} = \frac{\int_0^T \text{activeWorkers}(t)\,dt}{\max(\int_0^T \text{effectiveCapacity}(t)\,dt, 1)}$$
  *(Note: When a node has capacity 0 during a full outage across the window, utilization reports `0` and runtime status clearly shows `FAILED`.)*
